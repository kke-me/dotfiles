# PR Summary

## 手順

1. ユーザーが指定した差分・コミット・説明を優先する。
2. 指定がなければ、現在のブランチについて以下を確認する。
   - ベースブランチとの差分
   - 対象コミット
   - 変更ファイル
   - 実行済みテスト
3. 根拠のない目的、影響、テスト結果は記載しない。不明な重要事項だけ確認する。
4. 変更の目的、主要な技術要素、成果物への影響がレビュー順に伝わるよう要約する。
5. 次のフォーマットで、そのままPR本文に貼れるMarkdownだけを出力する。

## 出力フォーマット

```markdown
# PR: `<ブランチ名またはPRタイトル>`

## 概要

<変更内容と目的を2〜4文で記載>

### <主要テーマ・技術要素>について

<導入した仕組みや変更の背景、狙いを簡潔に説明>

### <対象システム・成果物>への影響

**<なし / あり — 影響の要約>**

| 変更 | 影響 |
|---|---|
| <変更項目1> | <具体的な影響> |
| <変更項目2> | <具体的な影響> |
| <依存関係> | <追加・更新したパッケージやバージョン> |

### 主な設定・仕様

<代表的な設定値、ルール、例外、環境差分などを記載>

---

## ファイル変更

| Before | After |
|---|---|
| `<変更前>` | `<変更後>` |
| `<なし>` | `<新規追加ファイル>` |

## コミット

- `<コミットメッセージ>`

### 確認すべきチェック項目

- [ ] ベースブランチ（マージ先）が正しいか確認する
- [ ] 単体テストコード更新/追加
- [ ] 単体テスト実行
- [ ] `npm run format && npm run lint` コマンドでコードをフォーマット
- [ ] コードへの適切なドキュメント追加 [TSDoc](https://tsdoc.org/)/[JSDoc](https://jsdoc.app/about-getting-started)
```

## 調整ルール

- `<対象システム・成果物>` は、変更に応じて `API`、`DB`、`UI`、`CloudFormation` など具体的な名前にする。
- 「主要テーマ・技術要素」が複数ある場合は、同じ形式の節を追加する。
- 該当しない行や節は、情報を捏造せず削除する。
- テストを実行していない場合、チェックボックスは未チェックのままにする。
- 文章は簡潔にし、コードを読めば分かる実装詳細の羅列は避ける。
